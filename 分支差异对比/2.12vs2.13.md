## 📋 **2-13 分支比 2-12 分支新增代码详解**

### **核心总结（结论优先）**

**2-13 分支在 2-12 的结算功能基础上，新增了「结算规则过滤责任链」，实现了结算前的多维度校验，包括：渠道黑名单校验、订单有效性校验、拼团时间校验等。**

**简单说**：

- **2-12**：直接结算（查询→更新）
- **2-13**：先过滤规则再结算（规则校验→查询→更新）

### **2.1 TradeSettlementRuleCommandEntity - 结算规则命令实体** ⭐


**字段含义**：

- `outTradeNo`：外部支付平台的交易单号（唯一标识一笔支付）
- `outTradeTime`：用户实际支付完成的时间（用于判断是否在拼团有效期内）

**为什么需要这个实体？**
- 统一封装结算请求参数
- 在责任链的各个过滤器之间传递请求信息

### **2.3 TradeSettlementRuleFilterFactory - 规则工厂** ⭐⭐

**作用**：装配责任链，将多个过滤器按顺序组装起来。

```java
package cn.bugstack.domain.trade.service.settlement.factory;

@Slf4j
@Service
public class TradeSettlementRuleFilterFactory {

    @Bean("tradeSettlementRuleFilter")
    public BusinessLinkedList<TradeSettlementRuleCommandEntity, 
            TradeSettlementRuleFilterFactory.DynamicContext, 
            TradeSettlementRuleFilterBackEntity> tradeSettlementRuleFilter(
            SCRuleFilter scRuleFilter,                    // ① 渠道黑名单过滤
            OutTradeNoRuleFilter outTradeNoRuleFilter,    // ② 外部单号校验
            SettableRuleFilter settableRuleFilter,        // ③ 可结算时间校验
            EndRuleFilter endRuleFilter) {                // ④ 结束节点
        
        // 组装责任链：scRuleFilter → outTradeNoRuleFilter → settableRuleFilter → endRuleFilter
        LinkArmory<TradeSettlementRuleCommandEntity, 
                   TradeSettlementRuleFilterFactory.DynamicContext, 
                   TradeSettlementRuleFilterBackEntity> linkArmory =
                new LinkArmory<>("交易结算规则过滤链", 
                    scRuleFilter, 
                    outTradeNoRuleFilter, 
                    settableRuleFilter, 
                    endRuleFilter);
        
        return linkArmory.getLogicLink();
    }

    // 动态上下文：在过滤器之间传递共享数据
    @Data
    @Builder
    @AllArgsConstructor
    @NoArgsConstructor
    public static class DynamicContext {
        private MarketPayOrderEntity marketPayOrderEntity;  // 订单营销实体
        private GroupBuyTeamEntity groupBuyTeamEntity;      // 拼团组队实体
    }
}
```


**执行顺序**：
```
SCRuleFilter → OutTradeNoRuleFilter → SettableRuleFilter → EndRuleFilter
   ↓              ↓                     ↓                    ↓
渠道黑名单     订单是否存在         时间是否有效        返回结果
```


**DynamicContext 的作用**：
- 在各个过滤器之间共享数据
- 第一个过滤器查询到的数据，后续过滤器可以直接使用

### **2.4 SCRuleFilter - 渠道黑名单过滤器** 🔴

**作用**：检查该渠道是否被拉黑（如下架的渠道不允许结算）。

```java
package cn.bugstack.domain.trade.service.settlement.filter;

@Slf4j
@Service
public class SCRuleFilter implements ILogicHandler<...> {

    @Resource
    private ITradeRepository repository;

    @Override
    public TradeSettlementRuleFilterBackEntity apply(
            TradeSettlementRuleCommandEntity requestParameter, 
            TradeSettlementRuleFilterFactory.DynamicContext dynamicContext) throws Exception {
        
        log.info("结算规则过滤 - 渠道黑名单校验{} outTradeNo:{}", 
                 requestParameter.getUserId(), requestParameter.getOutTradeNo());
        
        // 调用仓储层，检查是否在黑名单中
        boolean intercept = repository.isSCBlackIntercept(
            requestParameter.getSource(), 
            requestParameter.getChannel()
        );
        
        if (intercept) {
            log.error("{}{} 渠道黑名单拦截", 
                     requestParameter.getSource(), 
                     requestParameter.getChannel());
            throw new AppException(ResponseCode.E0105);  // 抛出异常，终止流程
        }
        
        return next(requestParameter, dynamicContext);  // 通过，继续下一个过滤器
    }
}
```


**底层实现**（DCCService）：
```java
// 从配置中心获取黑名单列表（如：s01c01,s02c02）
private String scBlacklist = dccService.getConfigValue("sc_blacklist");

public boolean isSCBlackIntercept(String source, String channel) {
    List<String> list = Arrays.asList(scBlacklist.split(","));
    return list.contains(source + channel);  // 如："s01c01"
}
```


**业务场景**：
- 假设某个渠道（如抖音小程序）合作到期下架了
- 运营人员在配置中心将 `s01c01` 加入黑名单
- 用户在这个渠道的支付将无法结算

**为什么要这样设计？**
- **灵活性**：不需要改代码，动态配置即可控制渠道
- **快速响应**：发现某个渠道有问题，立即拉黑
- **解耦**：业务代码不硬编码黑名单

### **2.5 OutTradeNoRuleFilter - 外部单号校验过滤器** 🔴

**作用**：验证订单是否存在，是否已退单。

```java
package cn.bugstack.domain.trade.service.settlement.filter;

@Slf4j
@Service
public class OutTradeNoRuleFilter implements ILogicHandler<...> {

    @Resource
    private ITradeRepository repository;

    @Override
    public TradeSettlementRuleFilterBackEntity apply(
            TradeSettlementRuleCommandEntity requestParameter, 
            TradeSettlementRuleFilterFactory.DynamicContext dynamicContext) throws Exception {
        
        log.info("结算规则过滤 - 外部单号校验{} outTradeNo:{}", 
                 requestParameter.getUserId(), requestParameter.getOutTradeNo());
        
        // 查询拼团信息
        MarketPayOrderEntity marketPayOrderEntity = 
            repository.queryMarketPayOrderEntityByOutTradeNo(
                requestParameter.getUserId(), 
                requestParameter.getOutTradeNo()
            );
        
        if (null == marketPayOrderEntity) {
            log.error("不存在的外部交易单号或用户已退单，不需要做支付订单结算:{} outTradeNo:{}", 
                     requestParameter.getUserId(), requestParameter.getOutTradeNo());
            throw new AppException(ResponseCode.E0104);  // 订单不存在或已退单
        }
        
        // 将查询结果存入上下文，后续过滤器可以直接使用
        dynamicContext.setMarketPayOrderEntity(marketPayOrderEntity);
        
        return next(requestParameter, dynamicContext);
    }
}
```


**校验逻辑**：
1. 根据 `userId` 和 `outTradeNo` 查询订单
2. 如果返回 `null`，说明：
   - 订单不存在
   - 或者订单已被删除（用户退单）
3. 抛出异常，终止结算流程

**为什么需要这一步？**
- 防止重复结算（用户已申请退款）
- 防止恶意攻击（伪造不存在的订单号）
- 保证数据一致性（只结算真实有效的订单）

### **2.6 SettableRuleFilter - 可结算时间校验过滤器** 🔴

**作用**：验证用户支付时间是否在拼团有效期内。

```java
package cn.bugstack.domain.trade.service.settlement.filter;

@Slf4j
@Service
public class SettableRuleFilter implements ILogicHandler<...> {

    @Resource
    private ITradeRepository repository;

    @Override
    public TradeSettlementRuleFilterBackEntity apply(
            TradeSettlementRuleCommandEntity requestParameter, 
            TradeSettlementRuleFilterFactory.DynamicContext dynamicContext) throws Exception {
        
        log.info("结算规则过滤 - 有效时间校验{} outTradeNo:{}", 
                 requestParameter.getUserId(), requestParameter.getOutTradeNo());
        
        // 从上下文中获取之前查询的订单信息
        MarketPayOrderEntity marketPayOrderEntity = dynamicContext.getMarketPayOrderEntity();
        
        // 查询拼团对象（包含有效期信息）
        GroupBuyTeamEntity groupBuyTeamEntity = 
            repository.queryGroupBuyTeamByTeamId(marketPayOrderEntity.getTeamId());
        
        // 用户支付时间
        Date outTradeTime = requestParameter.getOutTradeTime();
        
        // 关键校验：支付时间必须早于拼团结束时间
        if (!outTradeTime.before(groupBuyTeamEntity.getValidEndTime())) {
            log.error("订单交易时间不在拼团有效时间范围内");
            throw new AppException(ResponseCode.E0106);  // 超时支付
        }
        
        // 将拼团信息存入上下文，供后续使用
        dynamicContext.setGroupBuyTeamEntity(groupBuyTeamEntity);
        
        return next(requestParameter, dynamicContext);
    }
}
```


**业务场景举例**：

假设一个拼团：
- 创建时间：`2025-01-29 16:50:34`
- 拼团时长：24 小时
- 结束时间：`2025-01-30 16:50:34`

**情况 1：正常支付** ✅
- 用户支付时间：`2025-01-29 17:00:00`
- 判断：`17:00 < 16:50:34(次日)` ✓ 通过

**情况 2：超时支付** ❌
- 用户支付时间：`2025-01-30 17:00:00`
- 判断：`17:00 > 16:50:34` ✗ 超时，拒绝结算

**为什么要这样设计？**
- 拼团有过期时间，超时后不能参与
- 防止用户无限期拖延支付
- 保证拼团的时效性

### **2.7 EndRuleFilter - 结束节点过滤器** 🏁

**作用**：责任链的最后一个节点，负责封装并返回最终结果。

```java
package cn.bugstack.domain.trade.service.settlement.filter;

@Slf4j
@Service
public class EndRuleFilter implements ILogicHandler<...> {

    @Override
    public TradeSettlementRuleFilterBackEntity apply(
            TradeSettlementRuleCommandEntity requestParameter, 
            TradeSettlementRuleFilterFactory.DynamicContext dynamicContext) throws Exception {
        
        log.info("结算规则过滤 - 结束节点{} outTradeNo:{}", 
                 requestParameter.getUserId(), requestParameter.getOutTradeNo());
        
        // 从上下文中获取拼团对象
        GroupBuyTeamEntity groupBuyTeamEntity = dynamicContext.getGroupBuyTeamEntity();
        
        // 封装并返回完整信息
        return TradeSettlementRuleFilterBackEntity.builder()
                .teamId(groupBuyTeamEntity.getTeamId())              // 团队 ID
                .activityId(groupBuyTeamEntity.getActivityId())      // 活动 ID
                .targetCount(groupBuyTeamEntity.getTargetCount())    // 目标人数
                .completeCount(groupBuyTeamEntity.getCompleteCount()) // 已完成人数
                .lockCount(groupBuyTeamEntity.getLockCount())        // 锁单人数
                .status(groupBuyTeamEntity.getStatus())              // 拼团状态
                .validStartTime(groupBuyTeamEntity.getValidStartTime()) // 开始时间
                .validEndTime(groupBuyTeamEntity.getValidEndTime())     // 结束时间
                .build();
    }
}
```


**为什么需要单独的结束节点？**
- 统一返回格式
- 将上下文中分散的数据聚合到一个对象中
- 便于主服务直接使用返回结果

### **2.8 TradeSettlementOrderService - 结算服务（重构版）** ⭐⭐⭐

**作用**：使用责任链进行规则过滤后执行结算。

```java
package cn.bugstack.domain.trade.service.settlement;

@Slf4j
@Service
public class TradeSettlementOrderService implements ITradeSettlementOrderService {

    @Resource
    private ITradeRepository repository;
    
    // 注入责任链（由工厂自动装配）
    @Resource
    private BusinessLinkedList<TradeSettlementRuleCommandEntity, 
                               TradeSettlementRuleFilterFactory.DynamicContext, 
                               TradeSettlementRuleFilterBackEntity> tradeSettlementRuleFilter;

    @Override
    public TradePaySettlementEntity settlementMarketPayOrder(
            TradePaySuccessEntity tradePaySuccessEntity) throws Exception {
        
        log.info("拼团交易 - 支付订单结算:{} outTradeNo:{}", 
                 tradePaySuccessEntity.getUserId(), 
                 tradePaySuccessEntity.getOutTradeNo());
        
        // 【步骤 1】执行责任链规则过滤
        TradeSettlementRuleFilterBackEntity result = tradeSettlementRuleFilter.apply(
            TradeSettlementRuleCommandEntity.builder()
                .source(tradePaySuccessEntity.getSource())
                .channel(tradePaySuccessEntity.getChannel())
                .userId(tradePaySuccessEntity.getUserId())
                .outTradeNo(tradePaySuccessEntity.getOutTradeNo())
                .outTradeTime(tradePaySuccessEntity.getOutTradeTime())
                .build(),
            new TradeSettlementRuleFilterFactory.DynamicContext()
        );
        
        // 从过滤结果中获取团队 ID
        String teamId = result.getTeamId();
        
        // 【步骤 2】构建拼团实体（使用过滤结果中的数据）
        GroupBuyTeamEntity groupBuyTeamEntity = GroupBuyTeamEntity.builder()
                .teamId(result.getTeamId())
                .activityId(result.getActivityId())
                .targetCount(result.getTargetCount())
                .completeCount(result.getCompleteCount())
                .lockCount(result.getLockCount())
                .status(result.getStatus())
                .validStartTime(result.getValidStartTime())
                .validEndTime(result.getValidEndTime())
                .build();
        
        // 【步骤 3】构建聚合对象
        GroupBuyTeamSettlementAggregate aggregate = GroupBuyTeamSettlementAggregate.builder()
                .userEntity(UserEntity.builder()
                    .userId(tradePaySuccessEntity.getUserId())
                    .build())
                .groupBuyTeamEntity(groupBuyTeamEntity)
                .tradePaySuccessEntity(tradePaySuccessEntity)
                .build();
        
        // 【步骤 4】执行结算
        repository.settlementMarketPayOrder(aggregate);
        
        // 【步骤 5】返回结算信息
        return TradePaySettlementEntity.builder()
                .source(tradePaySuccessEntity.getSource())
                .channel(tradePaySuccessEntity.getChannel())
                .userId(tradePaySuccessEntity.getUserId())
                .teamId(teamId)
                .activityId(groupBuyTeamEntity.getActivityId())
                .outTradeNo(tradePaySuccessEntity.getOutTradeNo())
                .build();
    }
}
```


**与 2-12 版本的对比**：

| 步骤    | 2-12 版本    | 2-13 版本                          |
| ------- | ------------ | ---------------------------------- |
| **1**   | 直接查询订单 | **先执行责任链过滤**（4 个过滤器） |
| **2**   | 查询团队信息 | **使用过滤结果**（无需再次查询）   |
| **3~5** | 相同         | 相同                               |

**核心改进**：
- ✅ 增加了多层校验，提高安全性
- ✅ 过滤器复用查询结果，避免重复数据库查询
- ✅ 职责分离，每个过滤器只做一件事

### **3.1 group_buy_order - 拼团订单主表** ⭐⭐⭐

**表结构**：
```sql
CREATE TABLE `group_buy_order` (
  `id` int(11) unsigned NOT NULL AUTO_INCREMENT,
  `team_id` varchar(8) NOT NULL COMMENT '拼单组队 ID',
  `activity_id` bigint(8) NOT NULL COMMENT '活动 ID',
  `source` varchar(8) NOT NULL COMMENT '渠道',
  `channel` varchar(8) NOT NULL COMMENT '来源',
  `original_price` decimal(8,2) NOT NULL COMMENT '原始价格',
  `deduction_price` decimal(8,2) NOT NULL COMMENT '折扣金额',
  `pay_price` decimal(8,2) NOT NULL COMMENT '支付价格',
  `target_count` int(5) NOT NULL COMMENT '目标数量',
  `complete_count` int(5) NOT NULL COMMENT '完成数量',
  `lock_count` int(5) NOT NULL COMMENT '锁单数量',
  `status` tinyint(1) NOT NULL DEFAULT '0' COMMENT '状态（0-拼单中、1-完成、2-失败）',
  `valid_start_time` datetime NOT NULL COMMENT '拼团开始时间',
  `valid_end_time` datetime NOT NULL COMMENT '拼团结束时间',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uq_team_id` (`team_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```


**字段详解**：

| 字段               | 类型       | 示例值                | 含义                      | 为什么需要         |
| ------------------ | ---------- | --------------------- | ------------------------- | ------------------ |
| `team_id`          | varchar(8) | `"93125665"`          | 拼团唯一标识              | 区分不同的拼团     |
| `activity_id`      | bigint     | `100123`              | 关联的活动 ID             | 知道是哪个拼团活动 |
| `source`           | varchar(8) | `"s01"`               | 渠道（如微信、抖音）      | 统计各渠道数据     |
| `channel`          | varchar(8) | `"c01"`               | 具体来源（如小程序、APP） | 精细化运营         |
| `original_price`   | decimal    | `100.00`              | 商品原价                  | 计算优惠力度       |
| `deduction_price`  | decimal    | `10.00`               | 优惠金额                  | 显示省了多少钱     |
| `pay_price`        | decimal    | `90.00`               | 实际支付                  | 用户最终付款       |
| `target_count`     | int        | `3`                   | 需要几人成团              | 拼团目标           |
| `complete_count`   | int        | `2`                   | 已成功支付人数            | 还差几人成团       |
| `lock_count`       | int        | `2`                   | 下单未支付人数            | 防止超卖           |
| `status`           | tinyint    | `0`                   | 拼团状态                  | 控制业务流程       |
| `valid_start_time` | datetime   | `2025-01-29 16:50:34` | 拼团开始时间              | 计算有效期         |
| `valid_end_time`   | datetime   | `2025-01-30 17:05:34` | 拼团截止时间              | 超时判断           |

**数据示例**：
```sql
INSERT INTO `group_buy_order` VALUES
(1,'93125665',100123,'s01','c01',100.00,10.00,90.00,3,2,2,0,
 '2025-01-29 16:50:34','2025-01-30 17:05:34','2025-01-29 16:50:34','2025-01-29 17:13:02');
```


**解读**：
- 这是一个 3 人团（`target_count=3`）
- 已有 2 人支付成功（`complete_count=2`）
- 有 2 人下单但未支付（`lock_count=2`）
- 拼团还在进行中（`status=0`）
- 有效期 24 小时（`16:50:34` 到次日 `17:05:34`）

**为什么这样设计？**
1. **独立团队表**：一个团队包含多个订单，需要统一管理
2. **计数分离**：`complete_count` 和 `lock_count` 分开统计，清晰表达业务状态
3. **时间范围**：设置有效期，控制拼团的时效性
4. **唯一索引**：`team_id` 唯一，确保一个团队只有一条记录

**字段详解**：

| 字段             | 类型        | 示例值                | 含义           | 为什么需要           |

| `user_id`        | varchar(64) | `"xfg01"`             | 哪个用户下的单 | 关联用户信息         |

- 保证幂等性（同一笔支付不会重复结算）

**2. `out_trade_time`（外部交易时间）**
- 用户实际支付成功的时间
- **2-13 新增字段**，用于时间校验
- SettableRuleFilter 会检查这个时间是否在拼团有效期内

**3. `biz_id`（业务唯一 ID）**
- 组合格式：`activityId_userId_takeCount`
- 示例：`100123_xfg01_1` 表示用户 xfg01 参与活动 100123 的第 1 次订单
- 唯一索引约束，防止用户重复下单

```sql
INSERT INTO `group_buy_order_list` VALUES

 '2024-12-07 10:19:40','2025-12-07 10:19:40','9890001','s01','c01',
 100.00,10.00,1,'514260871457','0000-00-00 00:00:00',
```

- 用户 `xfg01` 参与了团队 `93125665`
- 订单号 `142771127603`，外部单号 `514260871457`
- 订单状态 `1`（已完成）
- 但 `out_trade_time` 是 `0000-00-00`，说明还没支付

**为什么这样设计？**
1. **订单一行记录**：每个用户的每次参与都有独立记录
2. **状态管理**：通过 `status` 控制订单生命周期（锁定→完成/退单）
3. **索引优化**：
   - `uq_order_id`：快速查询订单详情
   - `idx_user_id_activity_id`：查询用户参与记录
4. **时间记录**：记录支付时间，支持超时判断

### **3.3 notify_task - 回调任务表** ⭐⭐

**表结构**：
```sql

  `id` int(11) unsigned NOT NULL AUTO_INCREMENT,

  `parameter_json` varchar(256) NOT NULL COMMENT '参数对象',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```


**字段详解**：

| 字段             | 类型         | 示例值       | 含义       | 为什么需要           |
| ---------------- | ------------ | ------------ | ---------- | -------------------- |
| `activity_id`    | bigint       | `100123`     | 活动 ID    | 知道是哪个活动的回调 |
| `team_id`        | varchar(8)   | `"46832479"` | 团队 ID    | 通知哪个拼团成功了   |
| `notify_url`     | varchar(128) | `"暂无"`     | 回调地址   | 调用外部接口         |
| `notify_count`   | int          | `0`          | 已回调次数 | 重试计数             |
| `notify_status`  | tinyint      | `0`          | 回调状态   | 控制重试逻辑         |
| `parameter_json` | varchar(256) | `{...}`      | JSON 参数  | 传递给外部的数据     |

**数据示例**：
```sql
INSERT INTO `notify_task` VALUES
(1,100123,'46832479','暂无',0,0,
 '{"teamId":"46832479","outTradeNoList":["581909866926","155123092895","451517755304"]}',
 '2025-01-26 19:11:46','2025-01-26 19:11:46');
```


**JSON 参数解析**：
```json
{
  "teamId": "46832479",           // 拼团 ID
  "outTradeNoList": [             // 该团所有订单的外部单号
    "581909866926",
    "155123092895",
    "451517755304"
  ]
}
```


**业务场景**：
1. 拼团成功后，需要通知外部系统（如发货系统、积分系统）
2. 将回调任务写入数据库，而不是立即执行
3. 定时任务扫描 `notify_status=0` 的记录，执行回调
4. 回调失败后，可以重试（`notify_status=2`）

**为什么这样设计？**
- **异步解耦**：结算完成后不立即调用外部接口，而是写入任务表
- **可靠性**：即使外部接口挂了，任务记录还在，可以重试
- **可追溯**：记录回调次数和状态，便于排查问题
- **灵活扩展**：可以配置不同的回调地址
